# v0.6 TUI 与交互式 CLI 设计

> 状态：开发计划。本文描述目标接口，不代表当前已发布能力。

## 目标与边界

v0.6 为已有的安全运维 CLI 提供两个可选交互入口：全屏 TUI 与命令提示（REPL）。它们只组合公开的 Broker/Admin API；不直接操作 Redis key、SQLite 表、Stream 或 Consumer Group，也不改变 at-least-once、ACK、lease、dedup、DLQ/EQ 或 replay 的状态语义。

- **TUI**：适合本地持续观察、人工排障和受保护修复；推荐以 `Textual` 实现。
- **REPL**：适合 SSH 与键盘优先的排障；推荐以 `prompt_toolkit` 实现。
- **非交互 CLI**：保留给 CI、脚本和自动化，参数与退出码保持兼容。

安装为可选依赖：

```bash
pip install "taskflow[tui]"
taskflow tui --sqlite taskflow.db
taskflow shell --redis-url redis://host/2 --namespace payments
```

未安装 extra 时，`tui` 和 `shell` 必须返回清晰、可操作的安装提示；基础包不应导入 Textual 或 prompt_toolkit。

## 信息架构

### TUI 页面

1. **首页 / Health**：backend、脱敏连接标识、namespace、health 检查、错误/警告和刷新时间。
2. **队列总览**：队列名称及 READY、DELAYED、LEASED、DLQ、EQ、累计 counters；支持筛选、排序和分页。
3. **队列详情**：统计、配置/能力、consistency 结果及消息列表入口。
4. **消息详情**：状态、attempt、时间、delivery/consumer、失败原因、serializer/schema、dedup 摘要和 payload。
5. **DLQ / EQ**：分页列表、失败/过期详情和 replay 工作流。
6. **Consistency**：只读 check、dry-run proposal 与实际 apply 的独立确认界面。
7. **命令面板与帮助**：显示命令、快捷键、当前连接与风险级别。

默认快捷键：`?` 帮助、`r` 刷新、`/` 搜索、`:` 命令面板、`Esc` 返回、`q` 退出。界面必须可完全用键盘操作，并在窄终端中降级为单栏布局。

### REPL

建议使用上下文 prompt：

```text
taskflow[redis:payments]> health
taskflow[redis:payments]> queue use emails
taskflow[queue:emails]> inspect
taskflow[queue:emails]> dlq list
taskflow[queue:emails]> dlq show 01J...
taskflow[queue:emails]> consistency check
taskflow[queue:emails]> consistency repair --dry-run
```

首期支持 history、Tab 补全、`help [command]`、近似命令建议、结构化 JSON 输出和可复制的资源 ID。动态补全只查询分页/受限数据，不能在输入时触发无界扫描。

## API 与 capability 要求

现有 API 可直接支持 health、单队列 inspect、单消息 inspect、DLQ replay 和 consistency 工作流。跨 backend 的公共分页浏览 API 为：

```python
await broker.list_queues(cursor=None, limit=100)
await broker.list_message_summaries("emails", status=MessageStatus.READY, cursor=None, limit=100)
await broker.list_messages("emails", status=MessageStatus.READY, cursor=None, limit=100)
await broker.admin.page_expired("emails", cursor=None, limit=100)
```

`list_message_summaries()` 只读取消息元数据，绝不读取或解码业务 payload，适用于默认 TUI 列表；仅在用户显式显示 payload 时才使用 `observe_message()`。这些 API：

- 由公开 Protocol 表达，SQLite 与 Redis 都有测试；
- 返回有限页面、next cursor 和明确总数是否可得；
- 用 capability 表达 backend 或索引不支持的过滤器；
- 不要求扫描所有历史 ACKED 消息；
- 不因浏览操作创建 Consumer Group、写入 schema/key 或推进消息状态。

自动刷新仅调用严格只读 API。若 `inspect()` 等既有 API 会触发 maintenance，TUI 的默认刷新不得调用它作为隐式调度手段；应在 API 文档中单独标示该副作用并提供纯观察接口。

## 安全与危险操作

payload 一律默认 redacted。用户显式选择“显示 payload”后才在当前视图展示，并提示数据可能敏感；不得写入 shell history、TUI 日志、错误 toast 或默认剪贴板。Redis URL 的密码必须脱敏，dedup key 默认显示摘要而非完整值。

| 操作 | 默认行为 | 执行保护 |
|---|---|---|
| health / inspect / list / check consistency | 只读 | 无确认 |
| 显示 payload | 隐藏 | 显式用户操作与警告 |
| DLQ/EQ replay / delete | 不执行 | 影响摘要 + 二次确认；非交互 CLI 仍需 `--yes` |
| repair consistency | dry-run | 实际修复需风险摘要 + 二次确认；非交互 CLI 仍需 `--apply --yes` |

replay 成功只表示状态已被原子地从 DLQ/EQ 转移并重新投递。界面和命令输出使用 `replay_enqueued`，不得称作“业务成功”；可在后续刷新中显示 `ready`、`leased`、`acked`、再次 `dead_lettered` 等异步结果。

## 运行与性能

- 自动刷新间隔可配置且默认保守；刷新期间显示数据时间戳与加载状态。
- 所有列表使用分页；大队列、DLQ、EQ 和 Redis Stream 禁止一次性读全量。
- 关闭/崩溃时取消 UI refresh task 并关闭 broker 连接；不启动、停止或干预外部 worker。
- 非 TTY 不启动全屏界面，应提示使用现有 JSON CLI。
- Textual/REPL 层异常不得吞没 Admin API 错误；显示可诊断错误并保留非零退出码。
