# v0.7 开发计划：可诊断性、消息生命周期与调度体验

> 状态：规划中。v0.7 是以可靠性、API 人体工程学和运维体验为主的优化版本；功能完成后才将本文件中的验收项标记为完成。
>
> 本文补充 [开发路线图](roadmap.md)、[概念模型](concepts.md) 和 [运维说明](operations.md)，不改变 Taskqx 的 at-least-once、显式 ACK、lease 与业务幂等性要求。

## 1. 版本目标与边界

v0.7 聚焦以下四项：

1. 建立可用于生产排障的日志，尤其是 Worker handler 异常及重试耗尽时的原始异常和完整堆栈；
2. 重构 Broker / Message 提交 API，使从现有消息派生并重新投递任务成为一等、类型安全且不易误用的路径；
3. 完成独立于 Worker/claim/inspect 的 backend scheduler，使延迟消息、expiry、lease reclaim 和 ACK tombstone 清理能在空闲队列中可靠推进；同时完成 Redis 按 queue 的消息 keyspace 和迁移；
4. 持续优化 TUI；具体交互需求在开发过程中逐项补充进本文和验收清单。

v0.2 已具备 `submit(..., delay=timedelta(...))`、延迟 retry、`DELAYED` 持久化状态、SQLite/Redis 到期转 READY、过期转 EQ 及重启恢复；但到期迁移目前由 `claim()`、`inspect()` 或调用方显式 `maintain(queue)` 驱动。空闲队列没有独立维护进程时，延迟消息不会按时变为 READY，这不满足可靠延迟投递的产品要求。

因此 v0.7 不另起一套延迟状态机，而是在既有状态机上提供独立 backend scheduler，并把 expiry、lease reclaim 和 ACK 后保留期清理纳入同一维护责任。

非目标：

- 不承诺 exactly-once，也不把日志记录视作业务处理成功；
- 不在 TUI 中启动、停止或替代业务 Worker；
- 不引入通用工作流/DAG、优先级调度或业务 scheduler；backend scheduler 只推进既有消息生命周期状态；
- 不因 API 优化而直接修改 SQLite 表或 Redis key，所有状态迁移仍经 Broker/Store 的原子边界完成。

## 2. 可诊断日志与异常记录

### 2.1 目标行为

Worker 必须不再静默处理 handler 异常。每次异常至少产生结构化的失败上下文；当重试耗尽、消息进入 DLQ 或 retry/reject 状态迁移本身失败时，必须以 `ERROR` 级别记录**原始异常及完整 traceback**。

日志默认不得包含完整 payload、认证信息、完整 dedup key 或用户自定义 metadata 中的敏感内容。可关联日志与管理记录的最小字段为：

```text
backend, namespace, queue, message_id, delivery_id, consumer_id,
attempt, max_attempts, action, outcome, retry_delay, error_type
```

`workflow_id`、`parent_id` 和 dedup key 只记录安全摘要或由显式的 redact hook 决定。`exc_info` 必须传递原始异常，禁止仅记录 `str(exc)` 后丢弃栈信息。

### 2.2 日志分层和错误路径

- `DEBUG`：claim、ACK、延迟到期转 READY、heartbeat 等高频生命周期细节；默认关闭。
- `INFO`：Worker 启停、消息成功终结、显式 replay/repair 的安全审计摘要。
- `WARNING`：将要重试的 handler 异常、lease reclaim、单次可恢复 maintenance 失败；包含错误类型和关联字段。是否输出 traceback 应可通过 logger level/配置控制，但异常对象不可丢失。
- `ERROR`：retry 策略耗尽后的 DLQ、显式 reject 携带异常、handler 未处理异常无法完成 retry/reject、ACK/retry/reject 状态迁移失败、后台 maintenance 任务最终失败；必须带 `exc_info`。

特别约束：Worker 在“handler 抛出异常 → 计算 retry → 调用 delivery.retry()”这一链路中，应分别区分业务异常和状态迁移异常。后者不得覆盖前者；日志或异常链必须同时保留二者，确保排障时可确定消息是否已成功重新入队。

### 2.3 配置、扩展点与测试

- 使用标准 Python `logging` 命名空间 `taskqx` / `taskqx.worker`，由应用自行配置 handler、格式化器和日志采集；库不得调用 `basicConfig()`。
- 补充可选的 `LogContext` / redactor Protocol，统一产生安全 `extra` 字段，而不是让各 backend 自行拼接字段。
- 与既有 `EventSink`、Metrics 保持互补：日志面向人类排障，事件和指标面向程序化观测；同一失败不能因 sink 故障被吞没。
- 使用 `caplog` 覆盖 SQLite 与 Redis：首次 retry、retry 耗尽进入 DLQ、reject、retry 状态迁移失败、取消和 maintenance 失败；断言 traceback 存在、关联字段正确、payload 默认不泄露。

## 3. Broker / Message 提交 API

### 3.1 问题与设计原则

现有 `submit(queue, payload, metadata, ...)` 是扁平参数 API。它适合首次提交，却使“接收当前消息、深拷贝、只修改 payload 或少数字段、派生新消息”需要手工重写大量不变字段，并容易遗漏 dedup、过期、schema 或 lineage 信息。

v0.7 应以**提交草稿（submission draft）**作为统一输入模型，保留便捷关键字调用，但不继续为每个新字段扩张长参数列表。持久化后的 `TaskMessage` 仍是不可变消息事实；重新投递必须产生新的消息 ID 和创建时间，绝不能复用原消息 ID 或覆盖既有状态。

### 3.2 拟议公开 API

最终命名需在实现前 RFC 固化；推荐形态如下：

```python
message = delivery.message

# 深拷贝 JSON-compatible payload / metadata；保留可继承的提交字段。
draft = message.clone(
    payload={**message.payload, "page": 2},
    parent_id=message.id,
    dedup_key="page:2",
)

# submit 接受草稿、已持久化消息或传统关键字调用。
result = await broker.submit(draft)
# 等价的显式派生接口，适合需要固定 lineage 策略的场景。
result = await broker.submit_from(message, payload={"page": 2})
```

实现设计应满足：

- `TaskMessage.clone()` 返回可提交的独立草稿（或语义等价的 `SubmitRequest`）；它不返回带原 `id` 的“新消息”。`TaskMessage` 的 `id`、`created_at`、`available_at` 与运行时投递状态不是可继承的可变字段。
- clone 对 `payload`、`metadata` 及其中嵌套的 JSON-compatible `dict`/`list` 做深拷贝；调用方之后修改草稿不得影响原消息或已提交的消息。不可安全复制或不符合 serializer 约束的值应在提交准备阶段报出明确验证错误。
- 默认继承 queue、metadata、dedup、workflow、expiry、max_attempts 和 payload schema 等提交语义；每个字段均可显式覆盖或清除。`parent_id` 的默认策略须在 RFC 中明确，推荐默认指向来源消息以形成可追踪派生关系，并提供显式禁用方式。
- `broker.submit(TaskMessage)` 和 `broker.submit(SubmitRequest)` 均先归一化为草稿，再由 Broker 生成新 ID、时间和延迟可用时间。直接传入已持久化 `TaskMessage` 的行为必须与 `clone()` 一致并在文档中明确，不能静默复用它的 identity。
- `submit_many()` 接受同一提交输入模型，并定义 atomic / non-atomic 逐项错误语义；原有关键字 `submit()` 和 `SubmitRequest` 调用至少提供一个小版本兼容窗口及迁移告警。
- API 适配消息对象时必须完整保留现有 `delay`、serializer/schema、dedup TTL 和 lineage 能力，不能因新输入模型而丢失字段。

在实现前须完成 API RFC、类型 Protocol、迁移指南和示例，再进行任何破坏性改动。

### 3.3 验证重点

SQLite 与 Redis conformance suite 至少覆盖：clone 后原对象隔离、嵌套 payload/metadata 深拷贝、字段继承/覆盖/清除、每次提交获得新 ID、lineage、dedup 冲突、schema 校验、批量提交和失败回滚。旧式扁平调用必须有兼容回归测试。

## 4. 独立 backend scheduler、ACK tombstone 与 Redis keyspace

### 4.1 独立 scheduler

新增可独立部署、仅负责 backend maintenance 的 scheduler API / 运行入口；它不是 Worker，不领取业务消息，也不执行 handler。推荐使用显式生命周期对象：

```python
scheduler = broker.scheduler(
    queues=None,              # None 表示发现并维护 namespace 的所有队列
    interval=timedelta(seconds=1),
)
await scheduler.run()
```

Scheduler 必须可与生产者、Worker 分别部署，也可由应用作为独立进程运行；`start()` / `close()`、取消、异常退出和重启均有确定语义。一次 tick 对每个发现到的 queue 执行现有原子 maintenance 转移：

```text
DELAYED due        -> READY
READY / DELAYED / LEASED expired -> EQ
LEASED lease timeout -> READY 或 DLQ
ACKED tombstone due -> 清除业务 envelope，保留轻量状态 tombstone 与 message index
```

只允许一个 scheduler 实例运行不是正确性前提：SQLite 通过事务、Redis 通过 Lua/条件状态检查使同一 queue 的并发 tick 幂等，重复实例最多造成额外扫描。调度时间精度由 `interval` 决定，文档必须说明其延迟上界和容量参数。Redis 继续以 `TIME` 为状态机的权威时间；SQLite 使用 broker 注入时钟和事务内时间快照。

Redis scheduler 必须能发现动态 queue，不能要求业务预先在 `queues=` 配置中登记所有队列。为此新增 namespace 级 queue catalog，并在首次成功提交、replay 或显式创建 queue 时与相关状态原子登记；清空 queue / 迁移 / 删除 queue 时同步更新 catalog。SQLite 从持久化 queue 元数据发现队列。Scheduler 故障要有日志、健康检查和指标，且不影响独立 Worker 的正常消费。

### 4.2 ACK tombstone

每次 ACK 必须记录 `acked_at`，并以默认 5 分钟的 `ack_tombstone_ttl` 自动登记每 queue 的 cleanup
index。只允许 queue 的 `QueueConfig.ack_tombstone_ttl` 或 broker 的
`default_ack_tombstone_ttl` 调整正数 `timedelta`；不得要求单次提交配置。到期清理必须由 scheduler
原子清除业务 envelope 并移除 cleanup index，同时保留 ACKED 状态、message ID、queue、attempt、创建/确认时间、
serializer、最后操作/原因和 workflow/parent lineage。清理不得删除 READY、DELAYED、LEASED、DLQ 或 EQ
消息，且 ACK/replay/late delivery 与清理并发时必须以状态和 delivery token 防止误删。保留期内
`inspect_message()`、TUI 和审计 summary API 可读取 ACKED 消息；清理后 inspect 返回明确 not-found，
summary 仍标记 payload 已清除。`acked_total` 等累计计数必须保留，不依赖消息本体。DLQ/EQ 保留策略不在本项中
隐式改变，若后续需要须单独设计。

### 4.3 Redis 按 queue 消息 keyspace 与迁移

当前 Redis 不是“所有消息共用一个 Hash”：每条消息已使用独立 Hash，但 key 为：

```text
<namespace>:message:<message_id>
```

它没有 queue 前缀，导致按 queue 删除、备份、scan、容量治理和 slot-local 状态维护困难。v0.7 将迁移到：

```text
<namespace>:queue:{<queue>}:message:<message_id>
<namespace>:queue:{<queue>}:retention
<namespace>:queues                         # queue catalog
<namespace>:message-index                  # message_id -> queue，用于保留全局 inspect API
```

所有 Redis Lua scripts、提交 Store、状态机、Admin、consistency/repair、分页与 TUI 都必须改用该 keyspace。`message-index` 仅承担全局 ID 查找，不得成为所有可变 message state 的集中 Hash；`clear_queue()` 等未来维护操作只扫描/删除该 queue 的 hash-tag 前缀和 queue 自身索引。Redis Cluster 的 hash-slot 约束、key catalog 与 global index 的原子性边界必须明确；现有 standalone/Sentinel 语义不得变弱。

这是持久化 key 格式的破坏性变更。必须提供 schema/keyspace version、可重入迁移工具、dry-run、备份建议、迁移中断恢复和 v0.6 兼容读取窗口；不得在 `start()` 时无提示扫描并改写全部生产 key。新旧 key 并存期间，所有状态迁移只允许命中一种格式，防止同一消息被重复调度。

### 4.4 验收重点

SQLite 与 Redis 均须测试：空闲队列延迟消息仅依靠 scheduler 在到期后变 READY；重启恢复；多个 scheduler 并发；expiry/lease reclaim；tick 失败后恢复；动态 queue 发现；ACK 在保留期内可查、到期仅清除业务 envelope 并保留 summary lineage、不会误删其他终态。Redis 另须测试新 key 格式、按 queue 清理隔离、全局 message lookup、migration dry-run/升级/中断恢复及所有 Lua key/arg 布局。

## 5. TUI 持续优化

v0.6 的 TUI/REPL 设计、只读边界和危险操作确认仍为基线。v0.7 采用滚动需求清单：方向确认后在本节追加可验收条目，不以临时 UI 改动替代设计、测试和文档。

首批优化方向：

- DELAYED 消息的队列统计、分页浏览、详情中计划时间和 scheduler 健康/最后 tick 状态；
- Worker/DLQ 异常的安全错误摘要与相关 message ID 跳转，默认不展示 traceback/payload；
- ACKED 消息在保留期内的查询与剩余保留时间展示；
- 更清晰地区分“已调度 / 已重试 / 已进入 DLQ / replay_enqueued / 业务处理结果未知”；
- 刷新错误、断连和后台任务取消的可见反馈；
- 保持键盘操作、窄终端、无色终端、payload redaction 与只读刷新约束。

后续由产品方向补充页面、快捷键、筛选和交互流程；每项都必须声明只读/写入属性、确认机制、跨 backend capability 和测试场景。

## 6. 实施顺序与发布门槛

1. 先完成 scheduler/retention/keyspace RFC、Redis 迁移策略、提交 API 兼容性清单和日志字段/redaction 设计；
2. 为空闲队列 scheduler、ACK tombstone、Redis keyspace 迁移、Worker 异常链及 clone/submit 归一化编写跨 backend 测试；
3. 实现 scheduler、queue catalog、ACK tombstone 和 Redis 新 keyspace / 迁移工具，确认空闲队列 delay 可按期触发；
4. 实现日志基础设施和 Worker 错误路径，确认 retry 耗尽有原始 traceback；
5. 实现草稿/clone/新 submit API 及迁移兼容层；
6. 按确认的清单迭代 TUI，并更新 README、operations、示例和迁移文档；
7. 完成 SQLite、Redis、TUI optional extra、类型检查、lint、完整测试、构建和 wheel smoke。

发布前必须满足：

- [ ] retry 耗尽、DLQ 和状态迁移失败均有可关联的异常日志和原始 traceback，且默认日志不泄露敏感 payload；
- [ ] `TaskMessage` 派生/clone 与 Broker 消息输入 API 的 identity、深拷贝、lineage、dedup 和兼容语义已写入 API 文档与迁移指南；
- [ ] 独立 scheduler 在无 Worker、无 claim/inspect 活动的空闲队列中，仍能可靠地推进 due、expiry、lease reclaim 与 ACK tombstone；SQLite/Redis 的并发、重启和故障恢复测试通过;
- [ ] Redis message key 已迁移至 queue scoped 格式，queue catalog、全局 lookup index、按 queue 维护和可重入迁移工具均经测试；
- [ ] TUI 的新增功能遵守只读刷新、敏感数据保护和危险操作确认边界；
- [ ] `ruff check`、mypy、全量 pytest（含 Redis integration）、optional TUI 测试和 wheel 安装 smoke 全部通过；
- [ ] README、CHANGELOG、operations、示例和 v0.6→v0.7 migration 文档完成。
