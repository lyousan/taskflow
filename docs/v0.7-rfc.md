# v0.7 RFC：生命周期维护、提交草稿与 Redis keyspace

> 状态：已接受。本文固定 v0.7 的公开 API、持久化语义和迁移边界；实现必须遵守本文，后续变更需先修订 RFC。

## 1. 兼容性与发布策略

v0.7 保持 at-least-once、显式 ACK、lease、DLQ、EQ、去重和 `DELAYED` 状态语义。现有关键字 `submit()`、`SubmitRequest` 和 `submit_many()` 调用继续有效；新增输入模型与它们完全归一化到同一提交路径。已持久化消息绝不被原地重投递：每次提交均生成新的 ID、`created_at` 和（若有 delay）`available_at`。

Redis keyspace 是唯一的持久化破坏性变更。正式发布前提供 `taskqx redis migrate-keyspace`；运行中的 broker 不自动扫描或迁移 namespace。迁移前必须备份 namespace，并在所有生产者、Worker 和 scheduler 停止后执行。迁移器支持 `--dry-run`、可重入执行和中断恢复；旧格式只读兼容窗口至 v0.8，v0.7 实例不在同一消息上混用旧、新状态机。

## 2. 提交草稿和派生消息

`SubmitRequest` 是可提交草稿的公开名称。`TaskMessage.clone()` 返回新的 `SubmitRequest`，并深拷贝 JSON-compatible `payload`、`metadata` 及其嵌套 `dict`/`list`。该草稿没有 message identity 或运行时投递状态。

```python
source = delivery.message
request = source.clone(payload={**source.payload, "page": 2})
result = await broker.submit(request)
# 完全等价的显式入口：
result = await broker.submit_from(source, payload={"page": 2})
```

派生默认遵循以下规则：

- 默认继承 queue、payload、metadata、workflow、expiry、max_attempts、payload schema 和 delay 语义；`payload`、`metadata` 与所有可继承字段可显式覆盖。
- `parent_id` 默认设为 source ID。传入 `parent_id=None` 可显式创建无 lineage 的独立任务。
- `dedup_key`、`dedup_scope`、`dedup_ttl` 默认清除。复制业务去重键几乎总会造成无效的重复提交；需要继承时调用方必须显式传入全部三个字段。
- `expires_at` 是绝对时间，不会因 clone 延长。需要新 TTL 的调用方显式提供新的 `expires_at`。
- `payload_type` 默认由源消息保存的 schema identity 解析；只要 payload 未替换，提交会保留其 schema。传入新 `payload_type` 或未类型化 payload 遵循现有 schema 验证和清除规则。

`broker.submit()` 接受一个 `SubmitRequest` 或传统关键字调用；两种形式不可混用。`broker.submit_from()` 只接受 `TaskMessage`，先执行 `clone()` 再提交。`submit_many()` 接受 `SubmitRequest` 草稿列表，保持已有 atomic/non-atomic 语义。

## 3. 独立 scheduler 与 ACK tombstone

每个 broker 提供：

```python
scheduler = broker.scheduler(queues=None, interval=timedelta(seconds=1))
await scheduler.run()
```

`queues=None` 表示维护该 backend 已知的全部队列；显式队列仅维护给定队列。Scheduler 不消费、claim 或执行业务消息。`tick()` 执行一次维护并返回转移数量；`start()` 启动可取消的循环，`close()` 停止循环并等待当前 tick 完成，`run()` 等待至关闭或外部取消。多个 scheduler 可并行运行：SQLite 的事务和 Redis 的 Lua 条件迁移保证每条消息至多完成一次状态转移。

一次 tick 按 backend 权威时钟推进：

```text
DELAYED due                         -> READY
READY / DELAYED / LEASED expired    -> EQ
LEASED lease timeout                -> READY 或 DLQ
ACKED tombstone due                -> 清除业务 envelope，保留轻量状态 tombstone 与 message index
```

Scheduler 的最长正常到期延迟为 `interval` 加单次 tick 时长。其失败记录 `ERROR` 日志和 traceback，之后的 tick 继续运行；调用 `tick()` 时异常仍向调用方传播。

每次 ACK 都自动成为 tombstone：默认保留期为 5 分钟，由 broker 的
`default_ack_tombstone_ttl` 控制；`QueueConfig.ack_tombstone_ttl` 可对特定 queue 指定正数
`timedelta`。提交 API 不提供逐消息覆盖。ACK 时持久化 `acked_at` 并立即写入 cleanup index；仅
scheduler 在 `acked_at + tombstone TTL` 到期后清除业务 envelope 并移除 cleanup index，保留
message ID、queue、ACKED 状态、attempt、创建/确认时间、serializer、最后操作/原因和 workflow/parent
lineage。重放、迟到 delivery 或其他状态绝不能删除非 ACKED 消息。清理后 inspect 返回 `None`，而
summary/Admin/TUI 可继续查询这条轻量 tombstone，并明确显示 payload 已永久清除。

SQLite 通过 `messages(queue, status, retention_until)` 索引发现 tombstone 项。Redis 通过每 queue 的
`<namespace>:queue:{<queue>}:retention` zset 发现，score 为到期 Unix 时间戳。

## 4. Redis queue-scoped keyspace

新 keyspace：

```text
<namespace>:queue:{<queue>}:message:<message_id>
<namespace>:queue:{<queue>}:retention
<namespace>:queues
<namespace>:message-index
<namespace>:meta:keyspace_version
```

`message-index` 是 `message_id -> queue` 的只读定位索引，不承载 message state。queue catalog 是 Redis set，并在首次成功提交、replay 或显式 queue 初始化时登记 queue。列表与 scheduler 优先使用 catalog；仅在兼容窗口内可只读扫描旧格式。新格式所有脚本都以 queue 推导 message key，避免跨 queue 查询。

Redis Cluster 中 message hash、queue stream/index 和 retention key 共享 `{queue}` slot；全局 catalog 和 message index 不与 queue 状态放进同一 Lua 原子组。提交先完成 queue-local原子写入，再写全局定位索引；发现缺失 index 时只读 API 可扫描 queue catalog 修复内存定位，不修改状态。迁移器按 queue 迁移，并在完成单一 message 的所有 queue-local keys 后写入 index，确保新旧状态机不会同时处理同一 message。

## 5. 安全日志

库使用 `taskqx`、`taskqx.worker` 和 `taskqx.scheduler` logger，不调用 `basicConfig()`。每条失败日志的 `extra` 最小字段是 `backend`、`namespace`、`queue`、`message_id`、`delivery_id`、`consumer_id`、`attempt`、`max_attempts`、`action`、`outcome`、`retry_delay` 与 `error_type`。默认不会写 payload、metadata、认证信息或完整 dedup key。

可重试 handler 异常以 `WARNING` 记录；reject、重试耗尽、终结状态迁移失败和 scheduler tick 失败以 `ERROR` 加 `exc_info` 记录。handler 原始异常和 retry/reject 迁移异常分别记录，后者不得覆盖前者。
